# Studio Flows 2.0 Roadmap

Date: 2026-05-11
Status: Approved design — ready for planning

## Context

Studio Flows MVP shipped on `feat/flows-phase-6-react-canvas` with: visual canvas (xyflow), 4 trigger types (manual, webhook, schedule, collection event), ~10 operations across logic / data / communication / workflow groups, durable-workflow engine, REST API, Filament UI, basic execution logs.

This roadmap covers the four post-MVP phases that ship together as **flexpik/filament-studio 2.0**.

## Phases and order

| # | Phase | Branch | Rationale |
|---|---|---|---|
| 7 | Versioning & publishing | `feat/flows-p7-versioning` | Changes runtime contract and schema. Everything above inherits version semantics, so this must be first. |
| 8 | Security & permissions hardening | `feat/flows-p8-security` | Webhooks are already exposed. Highest real-world risk; sequenced before extensibility so the safety model is firm before third parties depend on it. |
| 9 | Extensibility API | `feat/flows-p9-extensibility` | Freezes a public registration API. Doing this before #7/#8 would force breaking changes on third parties when versioning / security shapes shift. |
| 10 | Observability & debugging | `feat/flows-p10-observability` | Pure additive UX on stable foundations. Safe to land last. |

Each phase has its own design doc in this directory:

- `2026-05-11-flows-p7-versioning-design.md`
- `2026-05-11-flows-p8-security-design.md`
- `2026-05-11-flows-p9-extensibility-design.md`
- `2026-05-11-flows-p10-observability-design.md`

## Release shape

All four phases ship together as **flexpik/filament-studio 2.0**.

- Integration branch: `release/flows-2.0` (long-lived).
- Each phase branch merges into `release/flows-2.0` only when its test suite is green and a smoke run on the integration branch passes.
- No phase begins until the prior phase has been integrated.
- Final cut: `release/flows-2.0` → `main`, tag `v2.0.0`, CHANGELOG entry, `MIGRATING.md` document.

## Acknowledged risks

- **Long-lived integration branch**: increases merge cost for later phases. Mitigated by sequential merging (no overlapping phase branches) and a passing test suite gate before each merge.
- **Breaking changes**: Phase 7 changes the runtime contract (no run without a published version). Phase 8 changes webhook auth defaults. Phase 9 freezes a public API surface. All breaking changes documented in `MIGRATING.md` shipped with 2.0.
- **Scope creep on Phase 10**: ships four observability surfaces simultaneously. Per-surface tests and explicit out-of-scope lists in the Phase 10 design keep it bounded.

## Out of scope for 2.0

Items from the original brainstorm intentionally deferred past 2.0:

- Run Script operation (needs sandboxing — significant security work).
- Branch-style drafts (Phase 7 chose strict single-draft semantics).
- Per-flow user ACLs (Phase 8 chose role-based + dangerous-op gates).
- Custom React canvas nodes for third parties (Phase 9 chose PHP + JSON-schema config only).
- Resume-from-failed-step replay (Phase 10 chose simple re-run with original payload).
- Marketplace / discovery service for third-party operations.
- External APM integrations (OpenTelemetry, Datadog, etc.).
- Multi-version concurrent publishing (e.g., A/B-style flow versions).

## Definition of done for 2.0

- All four phase branches merged into `release/flows-2.0`.
- Full test suite green on `release/flows-2.0` (host app + package).
- Browser smoke test passes against `release/flows-2.0` build.
- `MIGRATING.md` and `CHANGELOG.md` updated.
- `docs/extending/flows.md` (Phase 9 output) published.
- Tag `v2.0.0` cut on `main` after release-branch merge.
